# 菜单波次（Menu Waves）

> **Status**: In Design
> **Author**: user + agents
> **Last Updated**: 2026-11-03
> **Last Verified**: 2026-11-03
> **Implements Pillar**: 没有白吃的菜

## Summary

「菜单波次」把档口菜池按本局种子切成 3 波，一次只露出一波；吃掉当前波免费推进，主动跳过花 1 回合并永久失去剩余菜，最后一波可以免费「结束取餐」。`MENU_VISION` 只买下一波的部分预览，不买整波。它不改菜的价值，只改信息与到达顺序，让"等不等下一波"成为有代价的判断，也让腻度的重复惩罚在看不到整桌菜时真正生效。

> **Quick reference** — Layer: `Feature` · Priority: `Vertical Slice` · Key deps: `菜品数值`, `数据配置`

## Overview

「菜单波次」决定一局里玩家**什么时候**能看到哪几道菜。开局用本局种子把档口菜池切成若干波，一次只露出一部分；吃掉当前波或主动叫下一波时推进，被跳过的菜在本局不再出现。`MENU_VISION` 升级买的是"能提前看到几波"。它不改任何菜的价格或饱腹，只改**信息与到达顺序**：让"下一波会不会更好"成为一次有代价的判断，也让腻度的重复惩罚在看不到整张菜单时真正咬合。

没有它，12 道菜从第一回合就全部摊在桌上，最优餐可以被背下来；有了它，玩家必须在不知道后面有什么的情况下决定现在吃哪一口，而每一道被跳过的菜都是一次不可撤回的放弃。

## Detailed Design

### Core Rules

1. **职责边界** — 数据配置拥有 `dish_pool` 与波次参数；菜品数值拥有价格、饱腹与 `opt_value`；腻度与口味拥有重复惩罚。本系统拥有**波次划分、可见集、推进规则与信息可见度**，不改任何菜的价值、不读也不写腻度状态。
2. **开局一次性划分** — 用本局种子对 `dish_pool` 做确定性洗牌，再按 `wave_size` 顺序切片。每道菜在一局中恰好属于一波，不重复出现。划分生成后不再改变，玩家的选择不影响后续波的内容。
3. **只看当前波** — 玩家默认只能看到当前波的菜。未揭晓的波只显示剩余数量，不显示内容。
4. **吃完自动推进，免费** — 当前波的最后一道菜被吃下时，自动推进到下一波，不消耗额外回合。
5. **主动跳过花 1 回合** — 玩家可以在任何时候叫下一波：当前波剩余的菜本局消失，消耗 1 个回合。这是"等下一波"的唯一代价——没有它，玩家可以对任何洗牌免费跳过不想要的波，波次就只是显示顺序。
   **最后一波例外**：按钮变为「结束取餐」，**不消耗回合**，直接结束本局并丢弃剩余菜；本系统提供 `end_pickup() → ENDED`，餐局流程在最后一波的 `game_skip_wave` 路径调用它。没有这个出口，剩余容量放不下任何菜、回合却还有剩时，本局会卡死。
6. **跳过即失去** — 被跳过的菜在本局不再出现。代价不是回合，是那几道菜本身；回合代价只用于跨波。
7. **可见度升级买预览，不买整波** — `MENU_VISION` 每级揭示下一波中的若干道菜：`preview_dishes = min(menu_vision, wave_size − 1)`。**不提供"看到整波"**：12 道菜各出现一次时，看到两整波（8 道）就能推出第三波，等于全知。
8. **回合是共享预算** — 吃菜与跳过共用 `T` 个回合：`eats + skips ≤ T`。跳过不是免费的额外动作，它从同一份时间里扣。
9. **菜单健康（运行期，基准预计算）** — 开局按本局种子划分后，用**构建期预计算**的 `opt_value(pool, C0, T)` 表校验三件事：每波非空、划分恰好覆盖菜池一次、**可达最优落在基准的双侧带 `[0.9, 1.1]` 内**。基准是**本局实际菜池**（`pool_override` 非空时为覆盖池），`C0 = 20`、`T = turn_budget`、`cloying_resistance = 0`。未达标就换下一个种子重掷，最多 20 次；仍不达标则采用得分最高的一次并写 warning，不阻断开局。单次健康校验预算 ≤ 10 ms（12 道菜、3 波）；超预算时只检查每波非空与覆盖，跳过可达最优检查并写 warning。
10. **确定性** — 同一 `(station_id, seed)` 产生同一划分。洗牌只使用显式种子的随机数，不依赖字典遍历、资源扫描顺序或平台。
11. **可见度在开局锁定** — `menu_vision` 由「餐局流程」在开局传入并锁定。中途升级不改变本局的划分或预览。
12. **不聚合** — 本系统不计算总分、也不替玩家判断该吃哪道。它只回答"现在能看到哪些菜、下一波要花什么代价"。
13. **无菜可吃时交还控制权** — 以下任一情况向「餐局流程」发出"无可吃菜"信号，由后者结束本局：最后一波被吃完；玩家在最后一波选择「结束取餐」；没有剩余菜可选。回合还有剩余但无菜可吃，不是本系统的错误状态。
14. **与腻度的边界** — 波次只决定可见与到达顺序；腻度计数跨波保留，由「腻度与口味」自己维护。波次可以把"解腻菜"排在主菜之后，从而让腻度的顺序惩罚真正生效——这是两个系统叠加后才出现的效果，不由本系统计算。

### States and Transitions

本系统的状态是一局的划分、当前波索引与"本波剩余菜"。

| 事件 | 状态变化 | 说明 |
|---|---|---|
| 餐局开始 | 用 seed 生成划分；`wave_index = 0` | 划分与 `menu_vision` 一起锁定 |
| 吃下一道菜 | 从当前波移除该菜 | 若当前波变空 → 自动推进，不扣回合 |
| 主动"下一波" | 丢弃当前波剩余菜；`wave_index += 1`；回合 −1 | 只在非最后一波可用 |
| 最后一波"结束取餐" | 丢弃剩余菜；不扣回合；发出"无可吃菜"信号 | 玩家主动停止，避免无菜可吃时卡死 |
| 最后一波被吃完 | 发出"无可吃菜"信号 | 由「餐局流程」结束本局 |
| 餐局结束 / 重开 | 划分与索引整体丢弃 | 重开用新种子重新划分 |
| 数据配置尚未 `Ready` | 生成失败，带 station id 返回错误 | 不生成空波或占位菜 |

### Interactions with Other Systems

| 系统 | 方向 | 数据/接口 | 硬/软 |
|---|---|---|---|
| 数据配置 | 上游 | `get_station(id)` → `dish_pool`、`wave_size` | 硬 |
| 菜品数值 | 上游 | `opt_value`、各菜 `price` / `satiety`，用于可达最优校验 | 硬 |
| 腻度与口味 | 上游（只读） | 生成校验需要把重复惩罚计入可达最优；本系统不改腻度状态 | 软（强） |
| 餐局流程 | 双向 | `initialize(station_id, seed, turn_budget, menu_vision[, pool_override])`；`consume(dish_id) → {ADVANCED, NO_EATABLE, NONE}`（本波仍有菜时 `NONE`）；`advance()` 只承载付费跳波；`end_pickup() → ENDED`（最后一波结束取餐）；`get_run_menu() -> StringName[]`（本局有效菜单）；接收"无可吃菜"信号 | 硬 |
| 局内 HUD | 下游 | `visible_dishes`、`preview_dishes`、跳过代价、当前波索引 | 硬 |
| 局外升级 | 下游 | `MENU_VISION` 的语义由局外升级拥有；本系统只消费整数等级 | 软 |
| 结算与入场费 | 下游 | 本局实际吃到的菜与剩余回合 | 硬 |
| 首局引导 | 下游 | "波次会推进、跳过的菜不会回来"的教学数据 | 软 |
| 存档 | 条件 | 中途存档需保存 seed、`wave_index` 与本波剩余 | 条件 |

**接口所有权**：本系统拥有划分与推进规则；「局内 HUD」不得自行重排或补全未揭晓的菜，「结算」不得把没出现的菜算进菜单最优。`pool_override` 非空时，波次划分与健康校验都在覆盖后的菜池上运行；`consume` 负责吃空自动推进，`advance` 只负责付费跳波。

## Formulas

### 波次划分 `wave_partition`

The `wave_partition` formula is defined as:

`wave_count = ceil( |M| / wave_size )`

`W_i = shuffled(M, seed)[ i · wave_size : (i+1) · wave_size ]`，`i ∈ [0, wave_count)`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `M` | id 数组 | 1–N 道菜 | `StationData.dish_pool` | 档口菜池，顺序即洗牌前的输入 |
| `seed` | int64 | 任意 | 餐局流程 | 本局种子 |
| `wave_size` | int | 1–8 | `StationData.wave_size`（新增字段，默认 4） | 每波揭示的菜数 |
| `wave_count` | int | 1–N | calculated | 波数，向上取整 |
| `W_i` | id 数组 | 1–`wave_size` 道 | calculated | 第 i 波的内容 |

**Output Range:** `W` 是 `M` 的一个**有序划分**：每道菜恰好出现一次，所有波并起来等于 `M`。`|M|` 不能被 `wave_size` 整除时，最后一批只包含余数道菜，不补齐、不重复。MVP：`|M| = 12`、`wave_size = 4` → 3 波 × 4 道。

**Example:** 12 道菜、`wave_size = 4`、`seed = 42` → 洗牌后切成 `W_0`（4 道）、`W_1`（4 道）、`W_2`（4 道）。同一个 `(station_id, 42)` 在任何平台、任何帧序下都给出同一划分。

### 可见与预览 `visible_dishes` / `preview_dishes`

The `visible_dishes` formula is defined as:

`visible_dishes(run) = { d ∈ W_i : d 尚未被吃 }`

The `preview_dishes` formula is defined as:

`preview_dishes(run) = min( menu_vision, wave_size − 1, |W_{i+1}| )`，`i` 为最后一波时为 `0`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `i` | int | 0–`wave_count−1` | 本系统局内状态 | 当前波索引 |
| `menu_vision` | int | 0–∞ | 餐局流程（开局锁定） | `MENU_VISION` 升级提供的总预览额度 |
| `preview_dishes` | int | 0–`wave_size−1` | calculated | 下一波中被提前揭示的菜数 |

**Output Range:** `visible_dishes ⊆ W_i`；`preview_dishes ∈ [0, wave_size−1]`。上限是 `wave_size − 1` 而不是 `wave_size`：12 道菜各出现一次时，看到两整波就能推出第三波的全部内容，预览就失去意义。预览按洗牌顺序取下一波的前若干道。

**Example:** `wave_size = 4`、`menu_vision = 3` → 预览 3 道；下一波第 4 道仍然未知。`menu_vision = 4` 也只预览 3 道。

### 推进代价 `advance_cost`

The `advance_cost` formula is defined as:

```
advance_cost(run) =
  0   若 visible_dishes(run) = ∅            # 空波自动推进
  0   若 i = wave_count − 1                # 最后一波：结束取餐，直接结束本局
  1   其它                                 # 主动跳过剩余菜
```

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `visible_dishes` | id 集合 | 0–`wave_size` | calculated | 当前波还剩的菜 |
| `advance_cost` | int | {0, 1} | calculated | 推进到下一波消耗的回合数 |

**Output Range:** `{0, 1}`。空波自动推进**永远免费**——否则"把一波吃完"会同时付出吃菜的回合和推进的回合，双重收费。回合总预算：`eats + skips ≤ T`。

**Example:** 当前波还剩 2 道菜，玩家点"下一波" → 这 2 道本局消失，消耗 1 个回合。若玩家先吃掉这两道，波变空自动推进，不额外扣回合。

### 跳过对上限的影响

每主动跳过一波，就少一个吃菜的回合。按 104 元的最优餐（10 道）：

| 跳过次数 | 可吃菜数 | 可达上限 | 说明 |
|---|---|---|---|
| 0 | 10 | 104 | 最优集完整 |
| 1 | 9 | 100 | 去掉边际最低的白米饭（4 元 / 1 格） |
| 2 | 8 | 95 | 再去掉拍黄瓜（5 元 / 1 格） |

所以一次跳过的代价约为 **4–5 元**，不是"少一道菜"这么抽象——它正好是最优餐里最差的那道菜的分数。这是波次唯一真正咬合的地方：**没有回合代价的跳过会让任意洗牌都保持 104**。

### 可达最优 `wave_reachable_opt`

The `wave_reachable_opt` formula is defined as:

`wave_reachable_opt(M, seed, C, T, menu_vision) = max { Σ price(d) : s 是合法出餐序列 }`

合法出餐序列 `s` 是：按波序逐波进行；每一波内选择**一个有序子序列**吃掉（顺序影响腻度解腻）；可以随时花 1 回合结束当前波并丢弃剩余菜；满足 `Σ satiety_eff ≤ C` 与 `eats + skips ≤ T`。

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `C` | int | ≥ 1 | 胃容量系统 | 一局容量 |
| `T` | int | ≥ 1 | 时间与回合 | 一局回合数 |
| `satiety_eff` | int | 1–9 | 腻度与口味 | 实际饱腹，含重复追加 |
| `wave_reachable_opt` | int | 0–Σprice | calculated | 该划分下最优玩家能拿到的分数 |

**Output Range:** `[0, opt_value(M, C, T)]`，且永不超过静态最优。搜索空间在 MVP 下很小：每波 4 道菜的有序子序列共 65 种，三波合计约 2.7×10⁵ 条序列，生成期可穷举；不需要动态规划。

**Example:** 三波划分良好、无需跳过时 = **104**（静态最优完整可达）。若前两波各含一道最优餐之外的菜（炒青菜、海鲜锅），最优玩家各付 1 回合跳过 → 8 道菜 → **95**，仍在 0.9 阈值（94）之上。

### 菜单健康 `wave_healthy`

The `wave_healthy` formula is defined as:

`wave_healthy(M, seed) = (∀i: |W_i| ≥ 1) ∧ (⊎ W_i = M) ∧ (0.9 × opt_value(pool, C0, T) ≤ wave_reachable_opt ≤ 1.1 × opt_value(pool, C0, T))`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `opt_value(pool, C0, T)` | int | ≥ 0 | 菜品数值 | 本局实际菜池的静态最优；`pool_override` 非空时为覆盖池，否则为档口全池 |
| 双侧带 | int 区间 | ≥ 0 | calculated | `[0.9, 1.1] × opt_value(pool, C0, T)`；MVP 全池 104 → `[94, 115]` |
| `wave_healthy` | bool | {true, false} | calculated | 该划分是否可开局 |

**Output Range:** `{true, false}`。**注意这里校验的是可达最优，不是全池最优**——全池最优对任何洗牌都等于 104，用它做校验等于永远通过（死代码）。只有当菜池大于回合预算、或腻度的顺序约束被波次切断时，可达最优才会低于全池。

**Example:** 12 道菜、3 波、无跳过 → 可达 104 ≥ 94 → `wave_healthy = true`。前两波各含一道菜池外的菜（炒青菜、海鲜锅）时，最优玩家各付 1 回合跳过 → 8 道菜 → 95，仍通过。**当前参数下阈值偏宽，重掷很少触发**——0.9 × 104 = 93.6 的带宽能吸收两次跳过。只有当菜池大于回合预算（后续档口）、或腻度的解腻菜被波次切到无法插入时，可达最优才会真正跌破这条线；届时这个校验才成为主要闸门。

## Edge Cases

- **If 菜池大小不能被 `wave_size` 整除**：最后一波只包含余数道菜，不补齐、不重复画菜。12 / 4 整除，MVP 不会触发；下一个档口可能触发。
- **If 菜池小于 `wave_size`**：`wave_size` 在生成时钳制为 `|dish_pool|`，产生一波。单波等于全菜单可见，本系统在该档口退化为无波次——写进平衡报告，不报错。
- **If `wave_size < 1`**：视为配置错误，由数据配置在加载期拒绝。
- **If 某一波为空**：不可能由合法划分产生（划分恰好覆盖菜池）；若出现说明生成有 bug，`wave_healthy = false`，重掷种子。
- **If 最后一波被吃完**：不再有"下一波"动作；系统向餐局流程发出"无可吃菜"信号，由后者结束本局。
- **If 在最后一波点"下一波"**：按钮变为「结束取餐」，不扣回合，直接结束本局；剩余菜作废。这是主动停止，不是错误。
- **If 玩家把每一波都跳过/结束**：本局 0 道菜、净利 = −入场费。这是合法的失败方式，不是错误；结算照常展示。
- **If 一波被吃空**：自动推进，**不扣回合**，也不占用一次"跳过"。双重收费会让"吃完一波"变成惩罚。
- **If `menu_vision ≥ wave_size`**：预览仍钳制在 `wave_size − 1`。看到整波等于可以推出后续，预览失去意义。
- **If `menu_vision < 0`**：钳制为 0，不产生负预览。
- **If 中途获得 `MENU_VISION` 升级**：本局不生效。可见度在开局锁定，划分也不重排；下一局才生效。
- **If 当前波所有菜都放不进剩余容量**：菜仍显示（置灰 + 原因），玩家可以付费跳过；在最后一波则用免费的「结束取餐」退出。系统不自动跳过，也不允许 0 回合继续。
- **If 剩余回合为 0 而当前波还有菜**：本局结束，剩余菜作废；这是回合耗尽，不是跳过。
- **If 生成 20 次仍无健康划分**：采用得分最高的一次并写 warning，不阻断开局。与菜品数值"平衡问题不阻断启动"一致。
- **If 同一 `(station_id, seed)` 在不同平台生成**：划分必须完全一致。洗牌只能用显式种子的随机数，不得依赖资源加载顺序、字典遍历或浮点运算。
- **If 中途存档**：必须保存 `seed`、`wave_index` 与当前波剩余菜；只存"吃过的菜"无法还原未揭晓的波。
- **If 存档来自旧版本、菜池已变**：按存档的 `seed` 与当时的菜池重建；若 id 缺失，读档失败并回到菜单，不静默补菜。

**双向一致要求**：以上每个系统在编写自己的 GDD 时，必须在 Dependencies 中列出「菜单波次」为上游依赖。菜品数值的下游表中本系统仍是「GDD 未写」，需要在其下次修订时改为已写——本 GDD 不直接修改菜品数值。

**与「腻度与口味」的交叉契约**：波次可以把解腻菜排到主菜之后，使腻度的顺序惩罚真正生效；也可能把解腻菜切到无法插入的位置，让某局的可达上限下降。**这个后果由波次的生成校验负责**（`wave_reachable_opt` 已计入），不由腻度系统承担。腻度 GDD 的 Open Question 1 由本系统的 Core Rule 3/5 回答：可见集默认只有一波，且跳过有回合代价。

**与「结算与入场费」的校准契约**：0 次跳过时可达 104，与静态最优一致；1 次跳过约 100，2 次约 95。结算的历史最佳与校准应以实际可达值为参照，不能假设每局都能拿满 104。

**对外契约的稳定性**：`wave_size` 的语义（每波揭示数）与 `advance_cost = 1` 是跨系统契约。改这两项会同时影响可达上限、`MENU_VISION` 的价值与结算校准，必须先改本 GDD。

## Visual/Audio Requirements

- **当前波是唯一的"实物区"**：菜品卡正常显示；未揭晓的波只显示为占位槽（`?`）与剩余数量，不显示任何菜名、图标或价格。
- **预览是部分揭示**：被 `MENU_VISION` 揭开的下一波菜品按正常卡显示，其余仍是 `?`；不提供"全部揭开"按钮。
- **代价必须前置、但不弹确认（最后一波除外）**：非最后一波的按钮写明「跳过本波 · 放弃剩余 N 道 · 花 1 回合」，点击立即提交，不弹二次确认；最后一波的「结束取餐」打开 HUD 确认面板（见 `in-game-hud.md` 规则 16 / AC 25）。玩家在付出之前从按钮上看到代价。
- **零特效推进**：波次切换不做飞入、滑动、翻牌或延迟。占位槽直接变成卡片，或卡片直接消失。
- **不闪烁警告**：跳过不是危险操作，是计划动作；不用红色警示、不震动、不弹窗音。
- **音频不归本系统所有**。波次推进与跳过是否需要音效，由「音效反馈」决定；本系统只保证状态在同一帧可读。

> `art-director` not consulted — Lean mode（本系统是信息与流程层，视觉呈现归局内 HUD；概念文档的"数字优先 / 价目板"锚点已覆盖）。进入生产前需人工复核。

## Game Feel

- **跳过是一次"放弃"，不是一次"刷新"**：非最后一波的按钮写明放弃的菜数与回合代价，点击即时提交；最后一波的「结束取餐」弹出 HUD 确认面板。代价可见，操作不被打断。
- **回合数字当场减一**：付费跳过的那一帧，回合计数必须立刻变化，且与吃菜消耗走同一个计数器。玩家要对"时间和食物是同一预算"有肌肉记忆。
- **自动推进没有存在感**：吃完一波应该像翻到下一页，不打断心算、不播放动画。唯一的反馈是下一波出现。
- **`?` 槽制造的是好奇，不是焦虑**：占位槽不显示倒计时、不脉动。压力来自回合与容量，不来自"快来看下一波"。
- **失败可归因**：玩家应该能说出"我为了等清蒸鱼跳过了那一波，结果它没来"，而不是"这局随机不好"。跳过的菜在结算页可见（吃到的与放弃的分开列）。

## UI Requirements

- **波次条**：显示当前波索引（如 2/3）、当前波菜品卡、未揭晓波的 `?` 槽与数量。
- **跳过按钮**：文案写明代价（"跳过本波 · 放弃剩余 N 道 · 花 1 回合"）；最后一波变为「结束取餐」（免费），点击打开 HUD 确认面板（见 `in-game-hud.md` 规则 16 / AC 25）。
- **预览区**：`MENU_VISION` 揭示的下一波菜品正常显示；其余保持 `?`。不提供查看全部菜单的入口。
- **共享回合计数**：跳过与吃菜共用同一个回合显示；由「时间与回合」拥有，本系统只发起扣除。
- **不可选态**：放不进剩余容量的菜置灰并给出原因；这不阻止玩家付费跳过。
- **结算页**：分开列出"吃到"与"跳过/未吃"的菜，让放弃可见。
- **无障碍**：对比度 ≥ 4.5:1；`?` 槽必须同时有文字说明（"3 道未揭晓"），不能只靠图形；字号 150% 时不换行错位。

> **📌 UX Flag — 菜单波次**：本系统有 UI 需求。Phase 4 写 epic 之前，先用 `/ux-design` 为局内 HUD 的波次条、跳过确认与预览区出 UX 规格；相关 story 引用 `design/ux/hud.md`，不直接引用本 GDD。

## Acceptance Criteria

**划分与确定性**

1. **GIVEN** 任一 `station_id` 与 `seed`，**WHEN** 开局生成菜单，**THEN** 生成 3 个波次、每波恰好 4 道菜，12 道菜的并集等于完整菜池：无重复、无遗漏、总数为 12，每波非空。
2. **GIVEN** `(station_id, seed)` 固定，**WHEN** 在同一构建上连续开局两次，**THEN** 波次归属、波内顺序、每道菜的价格与饱腹逐项相同。
3. **GIVEN** 已提交的基准文件记录了 `(S01, seed=12345)` 的划分，**WHEN** 在第二个平台以相同参数开局，**THEN** 3 个波次的菜名与波内顺序与基准文件逐项相等。不同 `seed` 不要求划分不同，不作断言。

**可见性**

4. **GIVEN** 本局处于第 1 波，**WHEN** 打开菜单，**THEN** 仅第 1 波的 4 道菜显示菜名与数值；第 2、3 波各显示 4 个 `?` 占位并标注数量 4，不泄露菜名或数值；吃完第 1 波后，第 1 波的菜不再作为可选项出现。

**推进与跳过**

5. **GIVEN** 第 1 波已吃 3 道、回合计数 = 3，**WHEN** 吃下该波最后一道，**THEN** 自动进入第 2 波，回合计数 = 4（推进消耗 0 回合）。
6. **GIVEN** 第 2 波剩余 3 道、当前回合 = 5，**WHEN** 点击"下一波"并确认，**THEN** 回合计数变为 6（恰好 +1），这 3 道菜本局永久不可再获得：不出现在第 3 波，也不出现在结算的可选列表。
7. **GIVEN** 当前为第 3 波、剩余 2 道、当前回合 = 6，**WHEN** 点击「结束取餐」并确认，**THEN** 回合计数仍为 6，本局结束，剩余 2 道不计分，系统恰好发出一次"无可吃菜"信号。
8. **GIVEN** 已跳过 2 次、已吃 8 道、回合计数 = 10，**WHEN** 尝试吃第 9 道，**THEN** 操作被拒绝（本局已进入结算），`eats` 不变为 9，满足 `eats + skips = 10 ≤ 10`。
9. **GIVEN** 第 3 波仍有 2 道未吃、`eats = 10`，**WHEN** 结算，**THEN** 结束原因是"回合耗尽"，不发出"无可吃菜"信号，剩余 2 道不计分。

**预览升级**

10. **GIVEN** 开局 `menu_vision = 0`，**WHEN** 查看下一波预览，**THEN** 显示 0 道。
11. **GIVEN** 开局 `menu_vision = 2`，**WHEN** 查看下一波预览，**THEN** 恰好显示下一波的 2 道菜。
12. **GIVEN** 开局 `menu_vision = 5`，**WHEN** 查看下一波预览，**THEN** 显示 `min(5, 4 − 1) = 3` 道，任何情况下不显示第 4 道。
13. **GIVEN** 当前为第 3 波，**WHEN** 查看预览，**THEN** 显示 0 道（没有下一波）。
14. **GIVEN** 开局 `menu_vision = 1`，**WHEN** 局中升级到 3 后查看预览，**THEN** 本局仍只显示 1 道；下一局才使用 3。

**生成健康**

15. **GIVEN** 候选划分的 `wave_reachable_opt = 95`，**WHEN** 执行健康检查（阈值 94 = ⌈0.9 × 104⌉），**THEN** 通过、不重掷、尝试计数 = 1、采用该划分。
16. **GIVEN** 候选划分的 `wave_reachable_opt = 93`，**WHEN** 执行健康检查，**THEN** 触发重掷，最多 20 次；20 次仍未达标则采用最好的一次、写一条 warning、本局照常开始（不阻塞），检查函数不抛异常。

**边界与状态**

17. **GIVEN** 一份强制每一波都被跳过/结束的测试夹具，**WHEN** 结算，**THEN** `net = 0 − 85 = −85`，不崩溃，结算显示 0 道菜。
18. **GIVEN** 某 `seed` 下红烧肉在第 1 波、糖醋里脊在第 2 波，**WHEN** 第 1 波吃红烧肉、第 2 波吃糖醋里脊，**THEN** 后者消耗 5 格（基础 4 + 腻度 1），可用容量相应扣除。
19. **GIVEN** 跳过第 1 波、吃光第 2 与第 3 波共 8 道（`eats = 8`、`skips = 1`、回合 = 9），**WHEN** 吃下第 3 波最后一道，**THEN** 向餐局流程发出恰好一次"无可吃菜"信号，本局结束并出现结算界面。
20. **GIVEN** 第 2 波剩 A、B、C 三道，**WHEN** 点击"下一波"，**THEN** 立即提交、不弹二次确认，按钮已显示将失去 3 道；提交后三者不可再获得。
21. **GIVEN** 本波尚余 3 道，**WHEN** 吃下第 1 道，**THEN** `consume` 返回 `NONE`，`wave_index` 不变。
22. **GIVEN** 一个可达最优超出 `[0.9, 1.1] × opt_value(pool, C0, T)` 的候选划分，**WHEN** 健康校验，**THEN** 重掷；`pool_override` 非空时按覆盖池的 `opt_value` 计算基准。

> **测试夹具**：用例 3 需要 `(station_id, seed) → 划分` 的基准文件；用例 16 需要向健康检查注入一个必然不达标的候选生成器；用例 18 需要一个能固定"红烧肉在第 1 波、糖醋里脊在第 2 波"的 seed。三者都不得为通过测试而修改 12 道菜的真实数值。
