# 腻度与口味（Cloying & Taste）

> **Status**: In Design
> **Author**: user + agents
> **Last Updated**: 2026-11-03
> **Last Verified**: 2026-11-03
> **Implements Pillar**: 没有白吃的菜

## Summary

「腻度与口味」是一局的第二轴：按 `cloying_group` 统计本局已经吃过的同类菜，重复点选时追加饱腹；含 `酸` / `冰` 的菜可以解掉一个组的腻度，于是点菜顺序本身成为决策。它把静态最优餐从"背下来"变成"排对顺序"，并在单次可见菜单受限时提供真正的取舍。对下游系统，它只暴露一个数：这道菜此刻实际占几格。

> **Quick reference** — Layer: `Feature` · Priority: `MVP` · Key deps: `菜品数值`

## Overview

「腻度与口味」是《回本》里让静态菜单无法被一次算穿的运行期状态层。它按 `cloying_group` 统计本局已经吃过的同类菜，把重复选择变成额外的胃容量占用；并把 `taste_tags` 中的 `酸` 与 `冰` 变成解腻手段，让玩家可以通过点菜顺序消除累积的腻度。对玩家，它把"哪道菜单价最高"改写成"这一口放在第几位吃、和什么一起吃"；对下游系统，它是一组只读查询：给定本局历史，返回某道菜此刻的实际饱腹值，以及它是否还能吃下。

没有这一层，菜品数值就是一张静态表——最优解在第一局之后就被背下来，支柱 2「没有白吃的菜」失效。有了它，容量约束变成顺序约束：同一组数字在不同次序下给出不同答案，而答案仍然可以心算验证（支柱 1）。

## Detailed Design

### Core Rules

1. **职责边界** — 菜品数值拥有 `price`、`satiety`、`taste_tags`、`cloying_group` 的内容与静态派生值；本系统拥有**局内状态**（腻度计数）、**重复惩罚**与**解腻规则**。本系统不改价格、不改 `unit_value`、不改分组。
2. **状态按局存活** — 每个 `cloying_group` 一个整数计数。进入餐局时全部为 0，结算时整体丢弃。不跨局，也不参与局外成长。
3. **只按组计数** — `cloy(g)` 是本局已经吃掉的、`cloying_group` 为 g 的菜的数量。计数不看 dish id、不看价格、不看口味标签。这条是上游支配审查成立的前提：同组每道菜的惩罚必须相同。
4. **重复的代价是容量** — 吃一道菜时，若它所属的组已经被吃过 `c` 次，实际占用 `satiety(d) + min(c, cloy_cap)` 格。惩罚只加在饱腹上，不动价格：价格是得分，压力必须落在剩余容量上（支柱 3）。
5. **先付后记** — 额外饱腹用**吃之前**的计数计算；这道菜自己的计数在付完容量之后才 +1。所以一道菜永远不能用自己的计数抬高自己的代价。
6. **解腻自动触发** — 一道菜在计完自己的组之后，若 `taste_tags` 含 `酸` 或 `冰`，把**除自己组以外**计数最高的组减 1（下限 0）。并列时取「规范组序」里靠前的那一组。这是本作"解腻"的全部定义。
7. **解腻只结算一次** — 同时含 `酸` 与 `冰` 也只触发一次；找不到目标时什么也不发生，不积累、不顺延。
8. **解腻不退还已付的代价** — 已经因为重复多占的容量不退回；解腻只影响之后的选择。
9. **可吃性用实际饱腹判定** — 剩余容量不足以容纳实际饱腹时，该菜不可选（置灰并给出原因），不是"选了再弹错"。
10. **静态刻度不被改写** — `unit_value(d) = price/satiety` 仍是跨菜的静态刻度；局内玩家要算的是 `price / 实际饱腹`。本系统同时提供这两个数，但不新增、也不排序"有效单位价值"——排序权归玩家（支柱 1）。
11. **局内可见** — 额外饱腹、解腻目标、各组当前计数都必须在**选择之前**可见。任何隐藏修正都会把算术题变成背题。
12. **确定性** — 规范组序是一个显式数组，并列、目标选择与展示顺序全部按它；不依赖字典遍历顺序或哈希。MVP 规范组序取菜品数值表中的首次出现顺序：`主食, 蔬菜, 饮料, 甜, 蛋, 辣, 油, 鲜, 肉`。
13. **不聚合** — 本系统不计算一局总分或净值，只回答"这道菜此刻占几格"。求和由结算在 int64 中完成。
14. **口味标签在 MVP 只有一个作用** — `酸` / `冰` 触发解腻；其余标签是展示用的风味身份，不产生数值效果。完整的口味偏好与流派加成推迟到 Vertical Slice（见 Open Questions）。
15. **空组** — `cloying_group` 为空串的菜共享同一个空组计数（与菜品数值的支配规则一致）；MVP 菜单没有空组。未在任何菜单中出现的组不占状态。

### States and Transitions

本系统只持有一个按组索引的整数计数表，没有别的状态。

| 事件 | 状态变化 | 说明 |
|---|---|---|
| 餐局开始 | 所有组计数 = 0 | 由「餐局流程」在进入 Run 状态时触发 |
| 吃下一道菜 | 按**吃前**计数结算容量 → 该组计数 +1 → 若为解腻菜则目标组 −1（下限 0） | 三步顺序固定，不可交换 |
| 餐局结束 / 结账 | 整个计数表丢弃 | 不需要清理逻辑 |
| 重开一局 | 所有组计数 = 0 | 同"餐局开始" |
| 数据配置尚未 `Ready` | 查询返回错误，带调用者名与 dish id | 不返回 0、空组或默认菜 |
| 中途存档（若启用） | 计数表与规范组序一起写入 | MVP 无中途存档；见 Dependencies |

### Interactions with Other Systems

| 系统 | 方向 | 数据/接口 | 硬/软 |
|---|---|---|---|
| 菜品数值 | 上游 | `get_dish(id)` → `price`、`satiety`、`taste_tags`、`cloying_group`；`unit_value(d)` | 硬 |
| 餐局流程 | 上游 | 餐局开始 / 结束 / 重开三个生命周期事件 → 计数表重置或丢弃 | 硬 |
| 胃容量 | 双向 | 本系统给出 `effective_satiety(d)`；容量系统用它判定可吃性与"吃撑" | 硬 |
| 局内 HUD | 下游 | `extra_satiety(d)`、`cleanse_target(d)`（预览）、各组计数、不可选原因 | 硬 |
| 结算与入场费 | 下游 | 本局实际占用格数；设计期用它校准 `opt_value` | 硬 |
| 菜单波次 | 下游 | 本系统的强度依赖"单次可见集合小于全池" | 软（但见 Open Questions 1） |
| 首局引导 | 下游 | 讲解"重复加格"与"酸/冰解腻"的一件事 | 软 |
| 存档 | 下游 | 若启用中途存档，计数表必须随局内状态持久化 | 条件 |

**接口所有权**：本系统拥有额外饱腹与解腻规则；「胃容量」不得自行重算 `effective_satiety`，「局内 HUD」不得缓存一份独立的计数表——两处都会漂移。

## Formulas

### 额外饱腹 `extra_satiety`

The `extra_satiety` formula is defined as:

`extra_satiety(d) = min( group_cloy(group(d)), cloy_cap )`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `d` | DishData | — | 数据配置 `get_dish(id)` | 被评估的菜 |
| `group(d)` | string | 非空；空串视为同一组 | `DishData.cloying_group` | 该菜所属的腻度组 |
| `group_cloy(g)` | int | 0–N | 本系统局内状态 | 本局已经吃掉的、属于组 g 的菜数量（不含当前这道） |
| `cloy_cap` | int | 1–5（设计带）；schema 只要求 ≥ 1 | `StationData.cloy_cap` | 单道菜最多被追加的饱腹；当前值 3 |
| `extra_satiety` | int | 0–`cloy_cap` | calculated | 这道菜此刻多占的容量格 |

**Output Range:** `[0, cloy_cap]`。MVP 菜单里最大的组只有 2 道菜，所以 `group_cloy` 最多到 1，**上限 3 在 MVP 中永远不生效**；它是为后续档口更大的组保留的安全阀，不是当前平衡参数。`group_cloy ≥ 0` 由解腻的下限钳制保证。

> **未接入：抗性。** 数据配置的 `UpgradeData` 已定义 `CLOYING_RESISTANCE` 升级类型，概念文档也把「解腻」列为 MVP 三项升级之一，但本公式目前**不含抗性项**。在「局外升级」GDD 定义其数值语义之前，本系统按抗性 = 0 计算。接入时，抗性必须由「餐局流程」在开局时作为一局的修正传入，本系统不直接依赖「局外升级」——否则会与 `局外升级 → 结算与入场费 → 腻度与口味` 形成环。

**Example:** 本局已经吃过红烧肉（`肉`），再点糖醋里脊：`group_cloy(肉) = 1` → `extra_satiety = min(1, 3) = 1`，糖醋里脊实际占用 `4 + 1 = 5` 格。

### 实际饱腹 `effective_satiety`

The `effective_satiety` formula is defined as:

`effective_satiety(d) = satiety(d) + extra_satiety(d)`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `satiety(d)` | int | 1–6 | `DishData.satiety` | 静态饱腹 |
| `extra_satiety(d)` | int | 0–`cloy_cap` | calculated | 腻度追加 |
| `effective_satiety` | int | 1–(satiety_max + cloy_cap) | calculated | 局内实际占用格数，也是可吃性判据 |

**Output Range:** `[1, satiety_max + cloy_cap]`（MVP 为 1–7）。这是唯一允许参与容量判定的饱腹值；`satiety(d)` 只在展示"基础值"时出现。

**Example:** 糖醋里脊第二次属于 `肉`：`4 + 1 = 5`。静态单位价值 `18/4 = 4.50`，这一口的实际比值 `18/5 = 3.60`——玩家自己算，系统只给两个数。

### 解腻判定 `is_cleansing` / `cleanse_target`

The `is_cleansing` formula is defined as:

`is_cleansing(d) = (酸 ∈ taste_tags(d)) ∨ (冰 ∈ taste_tags(d))`

The `cleanse_target` formula is defined as:

`cleanse_target(d) = argmax_{g ≠ group(d), group_cloy(g) ≥ 1} group_cloy(g)`，并列时取规范组序最靠前者；无候选时为 `⊥`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `taste_tags(d)` | string 集合 | 0–3 项 | `DishData.taste_tags` | 风味标签 |
| `is_cleansing(d)` | bool | {true, false} | calculated | 这道菜是否触发解腻 |
| `cleanse_target(d)` | group \| ⊥ | 规范组序内 | calculated | 被减 1 的组；`⊥` 表示无效果 |
| `规范组序` | string 数组 | 9 项 | 本 GDD Core Rule 12 | `主食, 蔬菜, 饮料, 甜, 蛋, 辣, 油, 鲜, 肉` |

**Output Range:** `cleanse_target ∈ 规范组序 ∪ {⊥}`。**自己组永远不是候选**——否则糖醋里脊（`甜, 酸, 油`，属 `肉`）会抹掉自己的腻度，肉类的重复惩罚就永远不成立。含 `酸` 与 `冰` 两项也只返回一个目标。

**Example:** 已吃红烧肉（`肉 = 1`），再吃拍黄瓜（`酸`，属 `蔬菜`）：`蔬菜` 先 +1；解腻候选是除 `蔬菜` 外计数 ≥ 1 的组 → `肉 = 1` → `肉` 减到 0。之后吃糖醋里脊不再有额外饱腹。

### 结算顺序 `meal_step`

The `meal_step` procedure is defined as:

```
meal_step(d):
  1. e     = extra_satiety(d)                       # 用吃之前的计数
  2. 若 remaining_capacity < satiety(d) + e → 拒绝，状态不变
  3. remaining_capacity -= satiety(d) + e
  4. group_cloy[group(d)] += 1
  5. 若 is_cleansing(d)：
        t = cleanse_target(d)
        若 t ≠ ⊥ → group_cloy[t] -= 1               # t 的计数必然 ≥ 1，减后不会为负
```

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `remaining_capacity` | int | 0–`C` | 胃容量系统 | 本局剩余格数 |
| `e` | int | 0–`cloy_cap` | calculated | 本步追加饱腹 |
| `t` | group \| ⊥ | 规范组序 ∪ {⊥} | calculated | 本步解腻目标 |

**Output Range:** 每次调用使 `remaining_capacity` 减少 `satiety(d) + e`（≥ 1），并使**恰好一个**组的计数 +1，可能再使**最多一个其他**组的计数 −1。被拒绝时状态完全不变。

**Example:** 顺序 `红烧肉 → 拍黄瓜 → 糖醋里脊`：第一步 `肉 = 1`；第二步 `蔬菜 = 1`，解腻把 `肉` 归 0；第三步 `extra = 0`。三步共占 `3 + 1 + 4 = 8` 格。若把拍黄瓜放在红烧肉之前，解腻时 `肉` 还是 0（无目标），糖醋里脊就要多占 1 格，三步共 9 格——**同一组菜，顺序不同，代价不同**。

### 菜单腻度压力 `menu_cloy_pressure`

The `menu_cloy_pressure` formula is defined as:

`menu_cloy_pressure(M) = Σ_{g ∈ groups(M)} ( |{ d ∈ M : group(d) = g }| − 1 )`

**Variables:**

| Variable | Type | Range | Source | Description |
|---|---|---|---|---|
| `M` | id 集合 | 0–N 道菜 | 档口 `dish_pool` 或单次刷新菜单 | 被审查的菜单 |
| `menu_cloy_pressure` | int | 0–(N−|groups|) | calculated | 该菜单最多可能触发多少次重复惩罚 |

**Output Range:** `≥ 0`。`= 0` 表示菜单里每个组都只有一道菜，**腻度系统在这张菜单上完全失效**——这是可量化的"第二轴不存在"信号。可发布菜单要求 `menu_cloy_pressure ≥ 1`。当前 12 道菜池：蔬菜 1 + 鲜 1 + 肉 1 = **3**。

**Example:** 当前菜池 `menu_cloy_pressure = 3`，即一局最多有三道菜可能被追加饱腹；而静态最优餐只包含 `肉` 的一次重复，所以典型一局的裸惩罚上限是 1 格。

### 与校准值的关系

菜品数值的 `opt_value` 按静态饱腹计算（容量 20、10 回合 → 104 元）。加入腻度后，**104 仍然可达**，但需要一条正确的顺序：

> 红烧肉 → 拍黄瓜（解腻 `肉`）→ 糖醋里脊 → 其余七道任意

这条顺序共占 20 格、得分 104，与静态最优完全一致。因此：

- **`opt_value` 不需重算，入场费 85 与 `calibration_ratio = 1.224` 继续有效。**
- 本系统**不定义**受腻度约束的最优值。CI 只验证「存在一条零惩罚顺序」——给出见证顺序即可，不做状态空间搜索。
- 若某个菜单不存在零惩罚顺序（例如同一组有三道菜却没有足够的解腻菜），该菜单的实际上限低于 `opt_value`，校准必须按实际可达值重算。这是「菜单波次」在生成菜单时的责任。

## Edge Cases

- **If 某组的计数已经达到 `cloy_cap`**：继续吃该组时额外饱腹恒为 `cloy_cap`，不再增长。上限是安全阀，不是曲线——本作不做边际递增。
- **If 解腻菜找不到目标**（所有其他组计数为 0）：什么也不发生。效果不存起来、不顺延到下一道菜，也不折算成容量返还。
- **If 解腻菜自己所属的组是唯一计数非零的组**：无目标，同样什么也不发生。自己组被排除是硬规则——糖醋里脊永远不能解掉 `肉` 的腻。
- **If 一道菜同时含 `酸` 和 `冰`**：只触发一次，只减一个组。标签数量不构成倍率。
- **If 两个组的计数并列最高**：取规范组序 `主食, 蔬菜, 饮料, 甜, 蛋, 辣, 油, 鲜, 肉` 中靠前的那一组。顺序固定是为了可回放，不是因为它在设计上更重要。
- **If 解腻减到的不是玩家想解的组**：不做询问、不做选择，按规则执行；但 UI 必须在**吃之前**预览这次解腻的目标组。玩家看到的是结果，不是意外。
- **If 实际饱腹超过剩余容量**：该菜不可选（置灰 + 显示"需要 X 格，剩 Y 格"）。不弹错误、不允许透支、不自动跳过其他菜。
- **If `satiety = 0`**：上游数据配置已拒绝。本系统仍须断言并在除法或容量判定前报错，绝不产生除零或零占用。
- **If `cloying_group` 为空串**：所有空串菜共享同一个空组计数（与菜品数值的支配规则一致）。MVP 菜单没有空组，但规则先定好，避免下一个档口出歧义。
- **If 某组在当前可见菜单里已经没有菜，但计数仍大于 0**：计数保留到本局结束。解腻仍可以指向它——它记录的是一局的历史，不是当前菜单。
- **If 同一道菜被允许重复抽取（菜单波次）**：每次吃下都按正常流程让计数 +1，腻度按**出现次数**计，而不是按不同菜的数量计。当前 MVP 假设不重复抽取；若改为允许，本条即为实现依据。
- **If 结算时求和**：必须使用本局**实际付出的容量**（即 `effective_satiety` 之和），不是静态 `satiety` 之和。两个数在腻度生效时会不同，用错会让玩家的复盘对不上账。
- **If 中途存档**：计数表与规范组序必须一起持久化；只存"吃过的菜"列表会让解腻目标在读档后重算成另一个结果。MVP 不做中途存档，本条是为「存档」GDD 预留的契约。
- **If 重开一局**：计数表清零，不继承上一局的任何组状态。跨局残留是最容易被漏掉的 bug 类型。
- **If `cloy_cap < 1`**：视为配置错误，由数据配置在加载期拒绝；本系统不做静默修正。
- **If 菜单的 `menu_cloy_pressure = 0`**：游戏照常运行，但本系统在整局中完全不生效。这是可量化的可玩性缺陷，写进平衡报告，不阻断启动（与菜品数值的审查一致）。

**双向一致要求**：以上每个系统在编写自己的 GDD 时，必须在 Dependencies 中列出「腻度与口味」为上游依赖。菜品数值已经在下游侧列出本系统，但状态仍是「GDD 未写」，需要在它下次修订时改为已写——本 GDD 不直接修改菜品数值。

**对「菜单波次」的前置假设（本设计成立与否的关键）**：如果一局能看见并自由选择全部 12 道菜，10 回合吃掉 10 道，静态最优餐几乎就是整张表，只有 `肉` 会重复一次，而解腻菜本来就在最优餐里——于是腻度只是一道"记得把拍黄瓜放在两道肉中间"的顺序题，玩家错一次损失 1 格（约 4–5 元）。如果波次限制单次可见集合（例如每波 4 道），重复就变成被迫的取舍，本系统才真正提供支柱 2 要求的压力。**菜单波次的 GDD 必须显式回答这一点**；在此之前，本系统在 MVP 中的强度按"顺序谜题"评估，不按"资源约束"评估。

**对「结算与入场费」的校准契约**：`opt_value = 104` 只在存在零惩罚顺序时成立。当前 12 道菜池满足（见证顺序见 Formulas）。若未来菜单引入更大的组或更少的解腻菜，结算的校准必须改用实际可达上限，而不是无条件引用静态 `opt_value`。

**对外契约的稳定性**：`effective_satiety` 是跨系统契约。任何重定义（改惩罚轴、改解腻触发标签、改 `cloy_cap` 语义）都必须先改本 GDD，再改胃容量与 HUD；下游不得自行实现一份。

## Visual/Audio Requirements

本系统的视觉目标是**让惩罚在点下去之前就看得见**，不是让惩罚好看。

- **额外饱腹用追加形式，不覆盖原值**：菜品卡同时显示基础饱腹与实际饱腹（`3 → 5` 或 `3 +2`），追加部分用容量族的橄榄绿加深一档，不用回本红——回本红只属于正收益。
- **解腻预览必须前置**：选中一道解腻菜时，卡上直接写出"将解掉：肉 −1"。玩家在付款前就知道会发生什么；结算后才揭示等于把算术题变成抽奖。
- **不使用粒子、闪光、抖动、缩放**。唯一允许的动效是数字变化时的等宽字体原地替换，不做滚动。
- **腻度面板只显示计数 > 0 的组**，按规范组序排列；空组不占屏幕。
- **音频不归本系统所有**。解腻触发是否需要一个独立音效，由「音效反馈」决定；本系统只保证事件在结算前可读，不要求任何额外延迟。

> `art-director` not consulted — Lean mode（本系统是规则与状态层，视觉呈现归局内 HUD 与音效反馈；概念文档的"数字优先 / 价目板"锚点已覆盖配色原则）。进入生产前需人工复核。

## Game Feel

- **同一帧说清代价**：选菜界面上，实际饱腹的变化必须在选中态出现的那一帧完成，不等点击确认。心算的前提是"我看到的数就是我要付的数"。
- **顺序是有意义的，而且能被复盘**：正确的顺序保持 104 元 / 20 格；错误的顺序让第三道菜在容量上不可选。玩家失败时应该能说出"我该先吃拍黄瓜"，而不是"不知道为什么少了一格"。
- **解腻要有可感知的节拍**：吃下解腻菜后，被解掉的组计数当场归零并在面板上可见地消失——这是本系统唯一的"操作成功"反馈，不能延迟到下一回合。
- **不催促**：没有倒计时、没有自动推进。解腻是一个计划动作，不是反应动作（支柱 3）。
- **惩罚不升级为惩罚性反馈**：不闪红、不震动、不弹提示。玩家多占了一格是因为算错了，不是机器在责备他。

## UI Requirements

- **菜品卡字段**：名称、价格、基础饱腹、实际饱腹（含 `+N` 追加）、口味标签、不可选原因。价格与实际饱腹必须同屏可见，不得折叠。
- **解腻标记**：含 `酸` 或 `冰` 的菜在卡上有明确标记；选中时显示本次解腻目标组与 `−1`。
- **腻度面板**：按规范组序列出计数 > 0 的组及计数；不提供"按腻度排序"或任何把答案算给玩家的排序。
- **不可选态**：实际饱腹超过剩余容量时置灰，并写出"需要 X 格，剩 Y 格"。
- **结算页**：每道菜列出实际占用格数；总占用用实际值求和，必须能与局内看到的一致。静态 `unit_value` 的展示规则沿用菜品数值，不在此处重定义。
- **无障碍**：数字与背景对比度 ≥ 4.5:1；字号放大到 150% 时菜品卡与腻度面板不换行错位。完整要求见未来的 `design/accessibility-requirements.md`。

> **📌 UX Flag — 腻度与口味**：本系统有 UI 需求。Phase 4（Pre-Production）写 epic 之前，先用 `/ux-design` 为局内 HUD 的菜品卡与腻度面板出 UX 规格；相关 story 引用 `design/ux/hud.md`，不直接引用本 GDD。

## Acceptance Criteria

**容量与惩罚**

1. **GIVEN** 本局尚未吃过任何菜品（各组计数为 0），**WHEN** 选择冰淇淋（7 元 / 1 格，甜），**THEN** 该菜消耗 1 格，已用容量由 0 变为 1。
2. **GIVEN** 本局已吃红烧肉（16 元 / 3 格，肉），肉组计数为 1，**WHEN** 选择糖醋里脊（18 元 / 4 格，肉），**THEN** 实际格数 = 4 + min(1, 3) = 5，已用容量增加 5 格而非 4 格。
3. **GIVEN** 已依次吃红烧肉、白米饭、麻婆豆腐、炸鸡腿、清蒸鱼、炒青菜、番茄炒蛋、可乐（已用 16 格，肉计数 1），**WHEN** 尝试选择糖醋里脊，**THEN** 16 + (4 + 1) = 21 > 20，该菜不可选；已用容量保持 16，肉计数保持 1，重复尝试仍被拒。
4. **GIVEN** 空局，**WHEN** 按 红烧肉→可乐→糖醋里脊→白米饭→拍黄瓜→冰淇淋→番茄炒蛋→麻婆豆腐→炸鸡腿→清蒸鱼 选完 10 道，**THEN** 总价 104 元、已用容量恰好 20 格，全程无一次拒绝。

**解腻**

5. **GIVEN** 已吃清蒸鱼（鲜 1）、海鲜锅（鲜 2，实付 7 格）、红烧肉（肉 1），已用 13 格，**WHEN** 吃冰淇淋（甜，解腻），**THEN** 甜计数 +1，鲜由 2 减为 1，肉保持 1。
6. **GIVEN** 已吃麻婆豆腐（辣 1）、炸鸡腿（油 1），已用 4 格，**WHEN** 吃可乐（饮料，解腻），**THEN** 饮料 +1，辣由 1 减为 0，油保持 1（并列取规范组序靠前者）。
7. **GIVEN** 已吃麻婆豆腐（辣 1）、炸鸡腿（油 1）、清蒸鱼（鲜 1）、红烧肉（肉 1），已用 10 格，**WHEN** 吃冰淇淋（甜，解腻），**THEN** 仅辣由 1 减为 0，油、鲜、肉保持 1，已用容量变为 11。
8. **GIVEN** 各组计数为 0，**WHEN** 吃拍黄瓜（5 元 / 1 格，蔬菜，解腻），**THEN** 蔬菜 +1 且无任何组被减少，已用 1 格；随后选炒青菜，实际格数 = 2 + 1 = 3（证明解腻既不作用于自身组，也不储存）。

**状态与重置**

9. **GIVEN** 本局已吃红烧肉与糖醋里脊（肉计数 2），**WHEN** 重开本局，**THEN** 各组计数归 0，重开后先吃红烧肉仍只花 3 格。
10. **GIVEN** 本局依次吃红烧肉（3 格）与糖醋里脊（实付 5 格）后结束，**WHEN** 查看结算，**THEN** 已用容量显示 8 格（基础 7 + 腻度 1），净利 = 16 + 18 − 入场费；若在结算前再吃拍黄瓜解掉肉，已用容量只增加拍黄瓜的 1 格，之前多付的 1 格不退回。
11. **GIVEN** 同一次结算画面，**WHEN** 查看糖醋里脊的单位价值，**THEN** 显示 4.5（18 ÷ 4），不因实付 5 格而变成 3.6。

**边界**

12. **GIVEN** 当前 12 道菜固定菜单（蔬菜 / 鲜 / 肉 各 2 道，其余各 1 道），**WHEN** 计算菜单腻度压力，**THEN** 结果为 3。
13. **GIVEN** 已吃麻婆豆腐（辣 1）、炸鸡腿（油 1）、清蒸鱼（鲜 1），已用 7 格，**WHEN** 吃糖醋里脊（肉，含酸），**THEN** 肉 +1 并触发解腻，辣由 1 减为 0，已用容量变为 11（7 + 4）。

**可见性**

14. **GIVEN** 已吃红烧肉（肉计数 1），**WHEN** 在选择前查看糖醋里脊，**THEN** 界面显示基础 4 格 + 额外 1 格 = 实际 5 格。
15. **GIVEN** 已吃麻婆豆腐（辣 1）与炸鸡腿（油 1），**WHEN** 在选择前查看可乐，**THEN** 界面显示解腻目标为「辣」。

**确定性**

16. **GIVEN** 输入序列 红烧肉→可乐→糖醋里脊→白米饭→拍黄瓜→冰淇淋→番茄炒蛋→麻婆豆腐→炸鸡腿→清蒸鱼，**WHEN** 同一版本重复执行或回放两次，**THEN** 每一步后的各组计数、最终已用容量 20 格与总价 104 元完全一致。

**测试夹具（当前 12 道菜无法覆盖，需注入菜单）**

17. **GIVEN** 注入一个单组含 4 道菜的测试菜单，该组已吃 2 道（计数 2），**WHEN** 吃第 3 道，**THEN** 额外饱腹为 2 格。
18. **GIVEN** 注入一个单组含 5 道菜的测试菜单，该组已吃 4 道（计数 4），**WHEN** 吃第 5 道，**THEN** 额外饱腹为 3 格（受 `cloy_cap = 3` 钳制），不是 4 格。
19. **GIVEN** 菜单 M1 的每组只有 1 道菜、菜单 M3 的某一组有 3 道菜，**WHEN** 分别计算 `menu_cloy_pressure`，**THEN** M1 = 0（本系统不生效）、M3 = 2。
20. **GIVEN** 注入两道 `cloying_group` 均为空串的测试菜，**WHEN** 依次吃下，**THEN** 第二道额外饱腹为 1 格（两个空组视为同一组）。

> 夹具 17–20 依赖一个可注入的测试菜单（常量文件或工厂函数），不得为通过测试而修改 12 道菜的真实数值。
